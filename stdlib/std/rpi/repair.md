# Repair
Read the latest verification findings in `<host-verification-findings>` (and the previous verification artifact) and owning design documents. Fix the concrete failures, including their underlying cause. Distinguish between test failures (exit code ≠ 0) and harness receipt violations (stale workspace, untracked changes). If automated tests passed, do not invent or speculate on unobserved code bugs; resolve the command sequence or workspace cleanliness issues reported. Follow latest owner feedback. Run targeted checks and record changes, outcomes and remaining issues. If design assumptions were wrong, document the corrected decision and its consequences without erasing the original evidence. Submit an updated implementation/repair record. Fresh independent verification follows; repair-stage receipts do not count as verification evidence. The workflow has a run-wide maximum of three repair cycles.

If correction requires revisiting the owning design, add redesign_stage="system_design" or redesign_stage="program_design" to the repair submission. This restarts downstream design and implementation with updated evidence and still consumes this repair cycle. Never use redesign to reset the repair budget.
